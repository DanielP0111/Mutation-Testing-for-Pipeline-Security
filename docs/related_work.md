# Related Work

## Software Supply Chain Security and Pipeline Taxonomies
Securing software supply chains has motivated frameworks such as Supply-chain Levels for Software Artifacts (SLSA), which formalizes build integrity requirements across provenance, hermeticity, and isolated build workers. Recent empirical literature has categorized broader supply chain threats across package ecosystems (Ohm et al., 2020; Ladisa et al., 2023), identifying lifecycle script abuses and dependency confusion as dominant vectors. However, existing taxonomies frequently treat the build process as an atomic transition from source repository to published artifact, failing to model internal pipeline lifecycle phases where tampering can evade source code static analysis.

## Mutation Testing in Security and Defense Benchmarking
Mutation testing has long served as an empirical benchmark in software engineering to evaluate the adequacy of automated test suites by injecting synthetic, syntactic faults into program source code (Jia and Harman, 2011; Papadakis et al., 2019). While historically utilized for fault detection in application logic, mutation analysis has recently been adapted to security contexts, including fuzzing harness evaluation and policy rule validation. However, existing mutation frameworks operate exclusively on application source code rather than build system architectures.

The closest methodological precedent is MASC (Ami et al., 2021), which evaluates static crypto-API misuse detectors by mutation. MASC derives a taxonomy of 105 misuse cases from 40 academic and industry sources, abstracts them into 12 usage-based mutation operators, places mutants under three *mutation scopes* tied to an explicit threat model (an accidentally misusing developer, a developer whose fix introduces a new flaw, and an evasive developer), and checks that every mutant still compiles with the target project's own build scripts. Detectors are then run against the mutants, and *unkilled* mutants are traced to root-cause flaws: across nine detectors and over 20,000 mutants, MASC uncovered 19 previously unknown flaws, 59% of which surfaced only through mutation rather than through the base misuse cases.

Our framework adopts MASC's structure (taxonomy, then operators, then placement scopes, then an evaluation of misses) and moves it from application source code to the build pipeline. That move changes what a valid mutant is. A MASC mutant only has to compile, because the detector under test reads code. A build-pipeline mutant has to *execute* during the build to be an attack at all, and must do so while the build and its tests still pass, or a real attacker would be noticed. We therefore validate mutants dynamically against a clean baseline build (the `effective` level of §2.5) rather than by compilability alone, and we score defenses only on mutants that are known to work. MASC's own experience also motivates attention to build mechanics: one detector silently skipped most Android mutants because of multidex packaging, a build-level effect analogous to the cached-dependency behavior we document in §2.8.

## Build Code as an Attack Surface
Pappas and Gazzillo (2026) argue that build automation code should be secured like program code, and propose *phase isolation*: each development phase (configure, build, test, release) runs with a declared set of permissions, and an attack such as the XZ Utils backdoor is recognizable as a phase reading or writing what it should not. Their prototype, Foreman, runs each phase from a JSON specification and reports file accesses the specification forbids; on XZ Utils it flags the compile phase reading the malicious test archives. They identify a benchmark of safe and poisoned builds, drawn from real attacks and hand-crafted poisonings, as needed future work. Our benchmark addresses that need directly and evaluates Foreman as one of the defenses (§2.7). Unlike a fixed set of hand-crafted cases, mutation lets the same attack pattern be planted wherever it applies in a target project and lets defense coverage be measured per phase.
